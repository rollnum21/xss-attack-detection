1. Introduction

1. Introduction

1.1 Purpose

This Software Requirements Specification defines the functionality, interfaces, constraints, and quality requirements for the Cross-Site Scripting (XSS) Attack Detection System, named XSS Shield. It is a web-based educational analysis tool that examines a user-supplied string for a defined set of known XSS-related constructs. The document is intended for the student team, academic guide, evaluators, and future maintainers.

1.2 Scope of the System

XSS Shield accepts untrusted input through a browser interface or a REST API. It validates and normalizes the input, then checks deterministic rules across all four supported contexts: HTML_BODY, HTML_ATTRIBUTE, URL, and JAVASCRIPT. It returns an explainable classification, the contexts checked, matching rules, CWE-79 association, recommendations, and standards references.

  • In scope: Plain-text input analysis; automatic context scanning; deterministic rule matching; JSON API; safe result display; local browser history; JSON result export; light and dark interface themes; unit and API tests.
  • Out of scope: User authentication, database storage, real-time monitoring, WAF deployment, complete HTML parsing, exploit execution, automatic code repair, and guarantees that every XSS technique will be detected.
  • Expected benefit: A clear, repeatable demonstration of context-aware XSS pattern analysis and secure handling of untrusted input.

2. Overall Description

2. Overall Description

2.1 Product Perspective

The project is a self-contained web application. A Spring Boot application serves the browser interface and provides the REST API. No user account, database, external scanner, or third-party inference service is required for the implemented system.

+----------------+ POST /api/analyze +-----------------------+ | Browser User | ----------------------------> | Spring Boot API | | HTML/CSS/JS UI | | XssController | +----------------+ <---------------------------- +-----------+-----------+ | JSON result | | v | +-----------------------+ | | Detection Service | | | - Validation | | | - Normalization | | | - Context rule engine | | +-----------------------+

2.2 User Classes and Characteristics

User ClassTechnical ProficiencyPrimary Activities
Student / DemonstratorBasic to intermediateEnter a sample string, review the result, use example inputs, view history, and export a JSON report.
Developer / Security LearnerIntermediateInspect matched rule identifiers, contexts, recommendations, and linked security references.
API ClientIntermediate to advancedSend JSON requests to the API in automatic mode or an explicit supported context.

2.3 Operating Environment

  • Client: A modern browser capable of HTML5, CSS, and JavaScript. The interface is responsive for desktop and mobile widths.
  • Server: Java 17 runtime, Spring Boot, and embedded Tomcat.
  • Build: Apache Maven.
  • Communication: UTF-8 JSON over HTTP for local academic deployment; HTTPS is recommended when deployed beyond a local environment.
  • Storage: The last ten completed analyses may be stored only in the user’s browser localStorage. The backend has no database in the present scope.

2.4 Design and Implementation Constraints

  • The backend must remain a deterministic context-aware rule engine; it must not introduce arbitrary risk scores, percentage likelihoods, or AI confidence claims.
  • Submitted strings must be treated as data. They must never be executed by the backend or rendered as HTML by the frontend.
  • The project uses only the four documented contexts and a defined finite rule set.
  • The frontend and backend must exchange only the documented JSON request and response format.
  • The system is an educational detector and does not replace output encoding, sanitization, Content Security Policy, or secure framework usage.

2.5 Assumptions and Dependencies

  • The application is started locally using Maven and is reachable by the browser.
  • The user submits a textual string and does not rely on the tool to establish real application exploitability.
  • Internet access is optional for core analysis; it is only needed when the user opens linked OWASP or MITRE references.
  • The browser permits local storage if recent-analysis history and theme preference are to persist.

3. System Features and Functional Requirements

3. System Features and Functional Requirements

3.1 Module 1: Input and Automatic Context Scan

Req IDFeature DescriptionInput / Validation RulePriority
FR-1.1The system shall provide a text area for users to enter or paste an input string.Input is accepted as plain text and must contain at least one non-whitespace character before analysis.High
FR-1.2The system shall offer example strings for a script element, JavaScript URL, and normal text.Selecting an example replaces only the text area value; it does not execute the string.Medium

3.2 Module 2: Deterministic Detection Engine

Req IDFeature DescriptionInput / Validation RulePriority
FR-2.1The service shall reject blank input and invalid or missing context values with an INVALID_INPUT result.Blank input, unsupported context, or unreadable JSON body is invalid.High
FR-2.2The service shall normalize outer whitespace and case before rule matching.Normalization must not execute input, decode entities, or perform complex canonicalization.High
FR-2.3The service shall check rules for HTML_BODY, HTML_ATTRIBUTE, URL, and JAVASCRIPT in automatic mode.Each rule is evaluated only in its supported context or contexts.High
FR-2.4The service shall classify a match as KNOWN_XSS_PATTERN and a non-match as NO_KNOWN_XSS_PATTERN.No-match results must state that they are not a safety guarantee.High
FR-2.5The API shall accept a single explicit supported context for clients that know their output destination.Allowed explicit values are HTML_BODY, HTML_ATTRIBUTE, URL, and JAVASCRIPT.Medium

3.3 Module 3: Explainable Result Presentation

Req IDFeature DescriptionInput / Validation RulePriority
FR-3.1The frontend shall display the returned classification, contexts checked, matched-rule count, and server message.All displayed values originate from the API response or the submitted input.High
FR-3.2For each match, the frontend shall display rule ID, name, description, recommendation, matched context, CWE, and allowed security-reference link.Links are limited to approved HTTPS OWASP and MITRE hosts.High
FR-3.3The frontend shall display submitted input as plain text.Untrusted input must be assigned through safe DOM text APIs; unsafe HTML insertion is prohibited.High
FR-3.4The frontend shall offer download of the latest result as a JSON report.The report contains submitted input and the API response; users are informed it may contain sensitive data.Medium

3.4 Module 4: Local Convenience Features

Req IDFeature DescriptionInput / Validation RulePriority
FR-4.1The frontend shall retain at most ten completed analyses in browser-local history.History is stored only in browser localStorage when available and can be cleared by the user.Medium
FR-4.2Each history item shall show a shortened input, classification, automatic-scan label, timestamp, and Use Again action.Use Again copies the stored text back to the editor without executing it.Medium
FR-4.3The frontend shall provide a light/dark theme toggle and save the preference locally.The theme must maintain readable contrast and respect reduced-motion preference.Low

4.3 Software Interfaces

4.4 Communication Interface

The main interface is a REST request to POST /api/analyze. Request and response bodies use UTF-8 JSON and the content type application/json.

Request ExampleResponse Elements
{
  "input": "<script>alert(1)</script>",
  "context": "AUTO"
}
detected, classification, context, analyzedContexts, matchedRules, and message.

A valid analysis returns HTTP 200. Invalid input or an unreadable request body returns HTTP 400 with an INVALID_INPUT classification.

5. Non-Functional Requirements

PerformanceThe analyzer shall provide a responsive request state and render a result after the API responds. No artificial delay shall be added to simulate analysis.Manual browser walkthrough and API tests under normal local academic deployment.

7. Acceptance Criteria and Testing

7. Acceptance Criteria and Testing

7.1 Acceptance Criteria

IDAcceptance Criterion
AC-1Entering <script>alert(1)</script> in the web UI results in KNOWN_XSS_PATTERN and displays the relevant rule details.
AC-2Entering javascript:alert(1) results in a JavaScript URL-scheme match in the URL context.
AC-3Entering Hello, this is normal text. results in NO_KNOWN_XSS_PATTERN and displays the no-safety-guarantee explanation.
AC-4Blank input returns a structured INVALID_INPUT result.
AC-5Automatic browser analysis lists all four supported contexts as checked and labels each matched rule with its context.
AC-6Submitted input is shown as text and is never executed or inserted as HTML.
AC-7A completed analysis is added to local browser history; Use Again restores it to the editor; Clear history removes it.
AC-8The theme control persists the selected light/dark preference when browser storage is available.

7.2 Test Strategy

  • Unit tests: Verify normalization, rule matching, benign inputs, multiple matches, invalid requests, and each supported context.
  • Controller/API tests: Verify successful JSON responses, invalid request responses, response fields, and HTTP status behavior.
  • Manual UI checks: Verify example buttons, clear action, automatic scanning, result display, export, history, theme toggle, responsiveness, and keyboard focus.
  • Security checks: Confirm that test payloads remain inert text in the browser and do not execute.

The project shall not report invented accuracy, precision, recall, detection-rate, risk-score, or probability values. Any future metric must be calculated from documented test corpus results.

7.3 Known Limitations

  • The detector does not guarantee detection of every XSS technique.
  • Detection is limited to supported contexts and implemented rules.
  • Absence of a match does not prove that the input is safe.
  • XSS exploitability depends on the receiving application’s output handling and browser context.
  • The system is not a production Web Application Firewall and is not a replacement for encoding, sanitization, secure frameworks, or Content Security Policy.
